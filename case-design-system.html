01 / Challenge

A design system fails quietly.

One value changes in Figma and not in code. One component gets a state the others never had. Nothing breaks on the day; it drifts.

  1. ConsistencyTwenty-six components, one voice

    The same radius, the same focus ring, the same disabled colour, in every component and every state.

  2. TokensValues that live in two places

    A colour exists as a Figma variable and as a CSS custom property. Change one and the other goes stale.

  3. PlatformsThree screen sizes, one component

    Control heights, type sizes, margins and columns all differ between desktop, tablet and mobile.

  4. StatesTen or more states per component

    Hover, pressed, focus, loading, disabled, selected, error, success, read-only, indeterminate. Each needs a design and a rule.

  5. DriftDesign and code pulling apart

    A fix made in Figma but not in code, or the reverse, is invisible until a screen ships wrong.

  6. DocumentationGuidance that ages

    Spec cards, usage rules and code snippets fall behind the moment a component changes.

02 / Insight

One source. Every output.

Instead of treating tokens, components, documentation and code as separate deliverables that have to be kept in step by hand, the workflow connects them: one token file becomes the Figma variables and the CSS, and every component in both places is built on it.

03 / Architecture

Foundations to code, in one line.

The system is a hierarchy, and each layer only knows the layer beneath it. That is what keeps a change small.

  1. 01FoundationsType scale, elevation, motion, focus

    Text styles bound to platform variables. Elevation 1 to 3, a two-layer focus ring, a button highlight.

  2. 02Tokens4 collections · 147 variables

    Primitives (57) · Color (40, Light and Dark) · Dimension (20) · Platform (30, three modes). Every one scoped, with web, Android and iOS code syntax.

  3. 03Components26 sets · 359 variants

    Every fill, stroke, radius, padding, gap and height bound to a variable. State is always the last property; ten or more variants each.

  4. 04PatternsMessaging · Inbox · Bot builder · Widget

    Composites built from the atoms: message, composer, conversation item, node, launcher, rating.

  5. 05Screens3 sets · Light and Dark

    Product screens assembled from instances only, cloned to dark by switching the Color mode.

  6. 06Codetokens.css · components.css · product.css

    Generated tokens, hand-written component CSS checked in a browser, and a user guide shipped with the package.

Twenty-six components, one anatomy.

A few components explain the system better than a gallery of all of them. The button carries every rule; the input shows how states and sizes multiply.

  1. 01
    State is the last axis

    Variant=Primary, State=Hover. Columns read as states on every spec card, so a reviewer scans one row to see a variant finished.

  2. 02
    Ten variants, minimum

    Default, Hover, Pressed, Focus, Loading, Disabled at least; Selected, Filled, Error, Success, Read-only, Indeterminate where they mean something. Sets over thirty split.

  3. 03
    Text properties only for shared labels

    A hint or an error message differs per state, so it is content, not a property. A property default would overwrite every variant.

  4. 04
    Composites nest real atoms

    Card, Dialog, Tabs and Nav are made of Button, Badge and Tab instances, so a fix to the atom reaches every composite.

06 / Responsive

One component, three platforms.

Nothing is redrawn for tablet or mobile. The Platform collection changes control heights, type sizes, margins and columns, and every component bound to it follows.

  1. 01
    Touch gets taller

    Control heights step 40, 44, 48 for the medium size. The same button, the same tokens, a bigger target where a finger needs it.

  2. 02
    Layouts reflow by variable

    Columns 12, 8, 4; margins 64, 32, 16; a dialog becomes a bottom sheet and top-bar links become a bottom nav below 600 px.

  3. 03
    Type scales, styles don’t multiply

    Display is 56, 48 and 36, but it is one text style bound to one variable, so Figma and CSS agree without three copies.

07 / In products

The same parts, two very different screens.

An operator inbox and a bot builder share nothing on the surface and everything underneath: the avatar, the badge, the button, the focus ring, the radius scale, the colour aliases.

Rendered from product.css with neutral sample content. The patterns are modelled on customer-engagement products; nothing here is a client screen.
08 / Design meets code

Two lanes, one source.

The workflow is not a hand-off. Figma and code are generated and checked from the same file, and the hand-written parts are the decisions, not the typing.

Figma
create_variables.js

Four collections, Light/Dark and Desktop/Tablet/Mobile modes, scopes and code syntax on every variable.

Component sets

Anatomy, properties and the state matrix, built with Figma MCP scripts and bound to variables.

arrange_spec.js

Spec cards: states as columns, variants as rows, counts and axis keys.

Code panels

The CSS snippet beside its component, so designers and developers read one page.

tokens.json

Names, scales, aliases and modes. Written and owned by me.

Claude + Figma MCP

Runs the scripts, batched per page, against a state ledger so a build can pause and resume.

Code Connect

Each Figma component mapped to its class, so the inspector shows the real code.

Code
gen_css.js → tokens.css

The same names and values as the variables, as custom properties with theme and platform blocks.

components.css · product.css

Written first, by hand, on the tokens: one class per component, states as pseudo-classes and modifiers.

render_check.py

Every component rendered at 1280 light and 390 dark before a snippet goes anywhere near Figma.

audit.js

Unbound fills and strokes: zero. Web syntax on every variable. No open scopes. No banned names.

10 / Validation

Checked before it ships, and after.

A system earns trust by catching its own mistakes. These are the checks that run on every build, and the habits that keep the next one shorter.

  1. Automatedaudit.js

    Walks every component set: solid fills and strokes without a bound variable must be zero; every variable needs web code syntax; no variable may be open to all scopes; text is scanned for names that must not appear.

  2. Automatedrebind_props.js

    Cloning a variant in Figma drops its property references. Any set that was cloned is rebound before review.

  3. Validationrender_check.py

    Renders the component demo at 1280 wide in Light and 390 wide in Dark, in a real browser, before any snippet is pasted into a code panel.

  4. ReviewOne screenshot per phase

    Each build phase ends with a representative node screenshotted and checked; after a fix, only what changed is shot again.

  5. ProcessState ledger

    A state.json records pages, sets, icons and the remaining list after every phase, so a build can stop honestly and resume.

  6. EvolutionGotchas become rules

    Every mistake that cost a retry is written down with its fix. The next build starts from the rule, not the mistake.

  7. DocumentationUser guide, in Figma and in the package

    Principles, setup, how to read a spec card, state names mapped to code, do and don’t pairs from real instances, a developer checklist, a changelog.

11 / Reflection

A system is infrastructure, not a collection.

The components are the visible part. What makes the system hold is the connection underneath them: one token source that becomes variables and CSS, one anatomy every component shares, one set of checks before anything ships.

That connection is what lets design and development evolve together instead of drifting apart.
